# AGENTS.md

Контекст-документ для будь-якого AI-агента (Claude Code, Copilot, Cursor тощо),
що працює над цим репозиторієм. Мета — щоб агент розумів проєкт настільки,
щоб самостійно вносити зміни й перевіряти їх, а не лише генерувати код "наосліп".

## Що це за проєкт

Сервіс порівняння STEP-файлів (CAD, .stp/.step) на рівні дерева елементів
збірки. Для кожної деталі/підзбірки обчислюється обʼєм і центр ваги (ЦВ);
два файли порівнюються вузол-до-вузла (за назвою), результат — кольоровий
HTML-звіт (зелений/жовтий/синій/червоний = match/changed/added/removed).

## Архітектура

```
cli.py              — точка входу, аргументи командного рядка
src/step_tree.py     — STEP -> дерево (Node): парсинг через OCP (OpenCASCADE) XCAF
src/compare.py       — Node + Node -> DiffNode: порівняння двох дерев
src/report.py        — DiffNode -> HTML
tests/test_geometry.py — юніт-тести з еталонами (аналітичні формули обʼєму)
```

Ключова технічна деталь, яку МАЄ знати кожен агент перед правками
`step_tree.py`: обʼєм/ЦВ треба обчислювати з форми **компонента (інстанса)**,
а не "referred"-мітки деталі — інакше трансформація розташування в збірці
(TopLoc_Location) не застосовується і всі деталі показують ЦВ так, ніби
знаходяться в початку координат. Це вже було знайдено й виправлено один раз
(див. регресійний тест `test_cylinder_center_of_mass_reflects_assembly_location`).
НЕ РЕВЕРТУВАТИ цю логіку без оновлення тесту.

## Agentic-практики, застосовані в цьому проєкті

### 1. Контекст-інженерія (цей файл)
Замість того, щоб щоразу заново пояснювати агенту структуру проєкту й пастки
геометричного API OpenCASCADE, все це зафіксовано тут один раз.

### 2. Цикл "написав -> запустив -> перевірив -> виправив", а не одноразовий промпт
Розробка велась ітеративно: перша версія `step_tree.py` давала неправильний
центр ваги (компонент показував (0,0,0) замість зміщеної позиції). Це було
виявлено не "на око", а через порівняння з очікуваним результатом,
після чого код виправлено і додано регресійний тест, що фіксує саме цей баг.

### 3. Верифікація через незалежний еталон (a.k.a. evals)
`tests/test_geometry.py` не просто перевіряє "код не падає" — він звіряє
обʼєм примітивних тіл (куб, циліндр) з **аналітичною формулою**
(V_box = a·b·c, V_cyl = π·r²·h), обчисленою незалежно від коду парсингу.
Це і є "checker", який не довіряє власному виводу генератора на слово.

Запуск: `pytest tests/ -v`

### 4. Maker ≠ Checker
- Maker: агент, що пише код (`step_tree.py`, `compare.py`, `report.py`)
- Checker: (а) юніт-тести з аналітичними еталонами, (б) CodeRabbit
  на Pull Request (автоматичний рев'ю сторонньою моделлю), (в) окремий
  прогін іншого агента/людини з рев'ю діффу перед мерджем.
Maker не повинен сам собі підтверджувати, що зміна коректна — це підтверджує
незалежний крок.

### 5. Специфікація допусків порівняння як явний контракт
`compare.py` приймає `volume_tol_pct` і `com_tol_mm` — допуски, в межах яких
різниця вважається шумом вимірювання/експорту, а не реальною зміною
геометрії. Це задокументований контракт, який агент має зберігати при
рефакторингу, а не вбудовану магічну константу.

## Як агенту перевірити свою зміну перед комітом

```bash
pip install -r requirements.txt --break-system-packages
pytest tests/ -v
python3 cli.py tests/fixtures/sample_a.stp tests/fixtures/sample_b.stp -o /tmp/report.html
```

Якщо тести не пройшли — зміна не готова, незалежно від того, наскільки
"логічно правильним" виглядає код.
